# Findings

What the corpus showed when it was first run, on 16 and 17 November 2026,
against the latest release of twenty-five parsers, and against twelve programs
that apply patches. The numbers are in [`RESULTS.md`](RESULTS.md) and
[`APPLY.md`](APPLY.md); this file explains them, one kind of problem at a
time, and records what was already known to the projects.

Please keep three things in mind while reading.

- **These are hard cases.** Most of them are rare. Several of these libraries
  were written for one job — rendering a pull request, applying a patch
  generated by the same tool — and do that job well.
- **The adapters are mine.** Each library is reached through a small adapter
  (`adapters/`) that I wrote from its documentation and source. I checked every
  class below by calling the library directly, without the harness. If I have
  nevertheless misused a library, that is a bug in this repository: please open
  an issue and I will correct the record.
- **"Not found upstream"** means a targeted search of the project's issue
  tracker on that day found nothing. It is not a claim that nobody ever
  reported it.

Vector ids below (`git/paths/space`) are files under `corpus/vectors/`.
`node src/try.js <adapter> <vector-id> --raw` shows what a parser returns.

## 1. Quoted file names are not decoded

git wraps a name in double quotes and escapes it when it contains a control
character, a quote, a backslash or — by default — any byte outside ASCII:

```
diff --git "a/\303\274ber.txt" "b/\303\274ber.txt"
--- "a/\303\274ber.txt"
+++ "b/\303\274ber.txt"
```

That is `über.txt`. Thirteen of the twenty-five libraries return the escaped
text instead of the name, and two more decode only part of it
(`git/paths/non-ascii-quoted` and the other vectors tagged `quoted-path`). For
the JavaScript and Python libraries among them:

| parser | returns | 
| --- | --- |
| parse-diff, diff2html | `\303\274ber.txt` |
| gitdiff-parser | `/\303\274ber.txt"` (two characters cut off the front, the closing quote kept) |
| diffparser, whatthepatch | `"a/\303\274ber.txt"` (quotes and prefix kept) |
| what-the-diff, parse-git-diff | `"b/\303\274ber.txt"` |
| unidiff | `"a/\303\274ber.txt"`; its `path` property is `"\303\274ber.txt"` |
| patch-ng | `a/303/274ber.txt` — the backslashes become path separators |

jsdiff, libgit2, GitPython, go-gitdiff, sourcegraph/go-diff, reviewdog/diff
and diffy decode them, and so does JGit as long as nothing follows the closing
quote (section 2). This matters to anyone whose file names are not
English: with git's defaults, every `ü`, `é`, `文` or emoji in a path takes
this form.

Upstream: unidiff accepts quoted names since
[#110](https://github.com/matiasb/python-unidiff/pull/110) but does not
unquote them. Nothing found for the other projects.

## 2. A TAB is left on names that contain a space

When a name contains a space git ends the `---` and `+++` lines with a TAB, so
that the end of the name can be found:

```
--- a/my file.txt<TAB>
+++ b/my file.txt<TAB>
```

diff2html, gitdiff-parser, parse-git-diff and whatthepatch return
`"my file.txt\t"` (`git/paths/space`). Spaces in file names are ordinary on
macOS and Windows.

Upstream: diff2html's tracker has an earlier report about spaces in names,
marked fixed in 3.4.7; version 3.4.56 returns the TAB. Nothing found for the
others.

The TAB is also there when the name is quoted. A name with a space and a
letter outside ASCII gets both treatments:

```
+++ "b/\303\234bersicht 2024.txt"<TAB>
```

JGit 7.8.1 unquotes a name only when the closing quote is the last character
of the line, and here returns `\303\234bersicht 2024.txt"<TAB>`
(`git/paths/emoji-and-space-quoted`, `git/paths/double-quote`, and the three
GNU vectors with quoted names, where a timestamp follows the quote). Section 15
shows what that does to a patch.

Related: jsdiff, parse-diff, diffparser, patch-ng and libgit2 trim a trailing
space off a name that really ends with one (`git/paths/trailing-space`). That
case is exotic; it is listed for completeness. An open jsdiff pull request,
[#749](https://github.com/kpdecker/jsdiff/pull/749), touches the same area.

## 3. Content that looks like a file header starts a new file

Deleting the line `-- speed up lookups` from an SQL file produces the diff line
`--- speed up lookups`. diffparser 2.0.1 takes it for a file header and reports
a second file named `speed up lookups` (`git/content/deleted-double-dash-comment`;
ten vectors in all). parse-diff, from which diffparser was derived, counts the
lines of a hunk and is not affected. waigani/diffparser (Go, last changed in
2019) loses lines and names files after their content in the same vectors.

sourcegraph/go-diff 0.10.0 looks ahead instead of counting: a single
`--- comment` line is fine, but a deleted `-- a/x` directly followed by an added
`++ b/x` and then a hunk header — which is what `-U0` output looks like — is
taken for the start of a file. In `git/content/fake-header-pair-before-next-hunk`
it returns a second file, `secrets.env`, that is not part of the diff, and
attributes the following hunk to it. Its tracker shows the history of the
lookahead ([#54](https://github.com/sourcegraph/go-diff/issues/54),
[#55](https://github.com/sourcegraph/go-diff/pull/55)); nothing found for this
case.

Everywhere else this, the classic diff-parsing mistake, has become rare:
eighteen of the twenty-five libraries get all fourteen vectors of this kind
right. (Two Rust crates panic on them, and a Java library attaches the header
of the next file to the hunk before it; see section 14.)

The same trap exists in combined (merge) diffs, where a Markdown bullet
`- item` removed by the merge appears as `--- item`
(`combined/cc/markdown-bullets`).

## 4. Zero or omitted line counts are misread

`@@ -5,0 +6,2 @@` announces zero old lines; `@@ -1 +1 @@` omits both counts,
which means one.

- gitdiff-parser 0.3.1 computes `match[3] - 0 || 1`, so an explicit `0` becomes
  `1`: every added file, every deleted file and every pure insertion made with
  `-U0` gets `oldLines: 1` or `newLines: 1` (30 vectors, e.g.
  `git/basics/add-file`).
- diffparser 2.0.1 returns `0` for an omitted count (98 vectors, e.g.
  `git/basics/three-files`).
- whatthepatch 1.0.7 loses a line of the hunk in `git/ranges/u1-single-line-result`
  (`@@ -1,2 +1 @@`: the context line after the deletion is missing).
- unidiff 1.0.1 decides `is_added_file` from "one hunk that starts at 0 with
  length 0", so an existing empty file that receives content, and an insertion
  at the top of a file made with `-U0`, are reported as new files (5 vectors,
  e.g. `git/ranges/filled-empty-file`). Likewise `is_removed_file`.

Tools that ask git for `--unified=0` — to lint or measure only the changed
lines — meet zero counts constantly.

Upstream: nothing found.

## 5. File sections without hunks

An added or deleted empty file, a mode change, a pure rename, a binary file:
these sections have no `---`/`+++` lines and no hunks.

```
diff --git a/.gitkeep b/.gitkeep
new file mode 100644
index 0000000..e69de29
```

- **libgit2 1.9.7** (`git_diff_from_buffer`, here through pygit2) rejects the
  whole input when it contains an added or deleted empty file:
  `unexpected header line 4` (`git/ops/empty-file-added`). Known:
  [#6778](https://github.com/libgit2/libgit2/issues/6778), fixed on the main
  branch by [#7331](https://github.com/libgit2/libgit2/pull/7331), merged in
  August 2026; the 1.9.7 release does not contain the fix.
- **patch-ng 1.19.1** returns `False` for the whole patch when it contains a
  mode change, an empty file or a pure copy (18 vectors). Its source lists
  "git rename diffs and add/remove diffs" as to do. A rename with an edit comes
  back as two items, and binary sections are passed over silently.
- **parse-git-diff 0.1.0** returns no files at all for a diff that contains a
  `GIT binary patch` (`git/ops/binary-patch-literal`).
- **jsdiff, diff2html, gitdiff-parser** report a name on the side where no file
  exists: an added empty file has `oldFileName: "a/.gitkeep"` rather than
  `/dev/null`, although the same libraries report `/dev/null` for an added file
  that has content. The "new" flag is set correctly; code that tests the name
  is misled. **JGit** does the same (`getOldPath()` of an added empty or binary
  file is its name), against the documentation of `DiffEntry`, which says "file
  add: always /dev/null".

## 6. Names with spaces, where only the header carries them

`diff --git a/old name.txt b/new name.txt` cannot be split reliably; git
therefore adds unambiguous lines (`rename from old name.txt`). For a mode
change there are no such lines and the header has to be split by noticing that
both halves are the same path.

- **libgit2 1.9.7** rejects a rename between two names that contain spaces
  (`trailing data at line 3`, `git/paths/rename-with-spaces`), a mode change of
  a file whose name contains a space (`git diff header lacks old / new paths`,
  `git/paths/mode-change-with-space`) and a binary notice for such a file
  (`git/ops/binary-with-space-and-and`). Related earlier work:
  [#5029](https://github.com/libgit2/libgit2/issues/5029),
  [#5030](https://github.com/libgit2/libgit2/pull/5030). Nothing found for
  these three cases. Two more headers stop it, not searched upstream: a binary
  notice whose names are quoted (`git/ops/binary-with-non-ascii-name`) and
  the `dissimilarity index` line of `git diff -B`
  (`git/ops/rewrite-with-dissimilarity`).
- **unidiff 1.0.1** raises `Target without source` for a file below a
  directory named `a b` (`git/paths/space-then-b-slash`).
- **git 2.43.0 itself** cannot read this back:

  ```
  $ mkdir "dir " && … && chmod +x "dir /run.sh"
  $ git diff | git apply --check -R
  error: git diff header lacks filename information when removing 1 leading pathname component (line 4)
  ```

  `git apply` stopped at the first space that is followed by a slash. The fuzzer
  found this. It has since been fixed ("Keep going to find another SP" in
  `apply.c`): git 2.56.1 reads the same text without complaint. The case is in
  the corpus (`git/paths/directory-ending-in-space-mode-change`), marked as a
  vector that one of the three oracles could not confirm with git 2.43.

## 7. Text around the patch

`git format-patch` ends every mail with the signature separator `-- ` and git's
version number, directly after the last hunk:

```
 three
-- 
2.43.0
```

Read as a diff line, `-- ` is a deletion of the line `- `.

- **jsdiff 9.0.0** throws on every such mail: `Hunk at line 15 has more lines
  than expected` (`git-wrapped/format-patch`). Its release notes say that
  trailing text which could belong to a hunk is rejected on purpose; the
  signature falls under that rule. Known, with an open fix:
  [#729](https://github.com/kpdecker/jsdiff/pull/729).
- **whatthepatch 1.0.7** reports the signature as a deleted line, and in
  `git log -p` output appends the following commit's header and message to the
  preceding hunk.

diff2html, gitdiff-parser, diffparser and unidiff also stumble over one or both
of these inputs (extra lines in the last hunk, a miscounted deletion, or an
exception), and what-the-diff and parse-git-diff accept nothing in front of the
first `diff` line. None of those six documents support for wrapped
output, so RESULTS.md lists it outside their scope; it is worth knowing before
feeding them `git show` or a `.patch` file from a forge.

## 8. Lines are split or trimmed at characters other than LF

A diff line ends at LF. A carriage return, a form feed or U+2028 before it
belongs to the content.

- **whatthepatch 1.0.7** drops the CR of every line of a CRLF file and loses
  content at form feeds, vertical tabs and U+2028
  (`git/bytes/form-feed`, `git/bytes/unicode-line-separators`) — the behaviour
  of `str.splitlines()`.
- **diff2html 3.4.56** and **what-the-diff 0.6.0** drop the CR of CRLF lines;
  diff2html shows only `step 1` for the line `step 1\rstep 2\rdone`
  (`git/bytes/lone-cr-inside-line`), and what-the-diff's grammar throws on it.
- **parse-git-diff 0.1.0** cuts the function-context text of a hunk header at a
  CR or U+2028 (`git/content/section-heading-with-control-characters`).

- **sourcegraph/go-diff 0.10.0** and **reviewdog/diff 0.21.3** drop a CR at the
  end of every content line (`git/bytes/crlf-file-modified`).

For a renderer the missing CR is invisible. For a tool that applies or compares
patches it is a different file.

## 9. A line that reads `\ No newline at end of file`

A file can contain that text — documentation about diffs does, and so do stored
patch files. As content it always follows a marker character; diff2html removes
it anywhere in a line, leaving an empty line
(`git/content/no-newline-text-as-content`). Known:
[#598](https://github.com/rtfpessoa/diff2html/issues/598), fix proposed in
[#599](https://github.com/rtfpessoa/diff2html/pull/599).

## 10. Binary files

- **gitdiff-parser 0.3.1** never sets `isBinary` for git's ordinary output,
  because the `Binary files … differ` line is consumed by the loop that reads
  the header. Known: [#35](https://github.com/ecomfe/gitdiff-parser/issues/35)
  (open since 2024), [#22](https://github.com/ecomfe/gitdiff-parser/pull/22).
- **jsdiff 9.0.0** and **git-diff-view 0.1.8** recognise `Binary files … differ`
  but not `GIT binary patch` (`git diff --binary`). jsdiff: open pull request
  [#718](https://github.com/kpdecker/jsdiff/pull/718).

## 11. Other prefixes

Users set `diff.noprefix` or `diff.mnemonicPrefix`; scripts pass `--no-prefix`.

- With `--no-prefix`, parse-diff and diff2html still remove a leading `a/` or
  `b/` — which is then a real directory. Two different files,
  `a/readme.txt` and `b/readme.txt`, both come back as `readme.txt`
  (`git-config/noprefix/directories-named-a-and-b`).
- unidiff raises `Target without source` for a rename under `--no-prefix`,
  mnemonic or custom prefixes, and reports every file as renamed when the
  prefixes are unknown to it, because `is_rename` compares the two names.
- jsdiff and parse-diff leave the names of sections without hunks undetermined
  under such prefixes; jsdiff documents that.

- go-gitdiff removes the first path component of every name, as `git apply -p1`
  does. Under `--no-prefix` that is a real directory.

A tool that controls the git invocation can avoid all of this; see
[`SPEC.md`](SPEC.md#asking-git-for-a-diff-you-can-parse). The next section
shows what happens when it does not.

## 12. Tools that run git themselves

The libraries above are handed a diff. A tool that runs `git log -p` or
`git diff` itself and parses the result also inherits the user's git
configuration. [`extras/git-config-sensitivity`](extras/git-config-sensitivity/scan-under-configs.sh)
builds a small repository containing three random strings in the shape of
credentials, with an allowlist for a top-level `fixtures/` directory, and scans
it once per configuration:

```
gitleaks 8.30.1
default                exit 1  ['app/fixtures/ci.env', 'app/fixtures/prod.pem', 'config/deploy/settings.env']
diff.noprefix          exit 1  ['deploy/settings.env']
diff.mnemonicPrefix    exit 1  ['app/fixtures/ci.env', 'app/fixtures/prod.pem', 'config/deploy/settings.env']
color.ui=always        exit 0  []

trufflehog 3.99.9      the same two findings, with the same paths, in all four rows
```

- `color.ui=always`: git colours its output even into a pipe, no file section
  is recognised, and gitleaks reports "0 commits scanned … no leaks found".
  Known: [#2281](https://github.com/gitleaks/gitleaks/issues/2281), fix proposed
  in [#2284](https://github.com/gitleaks/gitleaks/pull/2284) (open since
  September 2026).
- `diff.noprefix=true`: git writes no `a/` and `b/`, so the path component that
  go-gitdiff removes is a real directory. Paths and fingerprints change
  (`config/deploy/settings.env` becomes `deploy/settings.env`), and the two
  findings below `app/fixtures/` turn into `fixtures/…`, match the allowlist
  `^fixtures/`, and are dropped. Not found in the tracker; #2284 does not cover
  it.

For contrast, diff-cover 11.0.2 — which gates pull requests on the coverage of
changed lines — passes `-c diff.noprefix=no -c diff.mnemonicprefix=no --no-color
--no-ext-diff` to git, and
[`diff-cover-changed-lines.py`](extras/git-config-sensitivity/diff-cover-changed-lines.py)
gets the same answer from it under every configuration tried, with spaces,
non-ASCII characters, TABs and quotes in the file names. (It does share the
" b/" problem of section 6: a file below a directory named `a b` is reported
as `c.py`.)

The parser is not at fault in the gitleaks case: the go-gitdiff fork agrees with git on every
vector in its scope and on some 23,000 random ones. The invocation is. Two more
options on the command line (`--src-prefix=a/ --dst-prefix=b/`) close the
second case, as `--no-color` closes the first.

## 13. Applying

Sections 1 to 12 are about reading a diff. This one is about acting on it.
208 of the vectors are patches in the plain sense — the vector records the tree
before and the tree after — and twelve programs were asked to get from one to
the other ([`APPLY.md`](APPLY.md) has every result; `node src/apply.js --adapter
gnu-patch --show` repeats one). A program may refuse a patch. What matters here
is the other outcome: it reports success, and a file is not what it should be.
I reproduced the cases of `git apply`, GNU patch, BusyBox patch, toybox patch,
libgit2, JGit and patch-ng by calling the program by hand, outside the harness;
the go-gitdiff case is the one its own tracker describes. toybox patch and JGit
were added a day later and have their own section, 15.

**Zero context.** A hunk made with `-U0` that only inserts has an old range of
length zero, `@@ -5,0 +6 @@`, and that range names the line *after which* the
new lines go.

| | `@@ -5,0 +6 @@` on a file of ten lines |
| --- | --- |
| `git apply` 2.43.0 | exit 0, the line is appended **after line 10** |
| `git apply --unidiff-zero`, GNU patch, jsdiff, whatthepatch, libgit2, JGit, diffy, java-diff-utils 4.18 | after line 5 |
| go-gitdiff 0.9.0, patch-ng 1.19.1 (and java-diff-utils up to 4.15) | no error, the line is inserted **after line 4** |
| BusyBox patch | exit 0, appended after line 10 |
| toybox patch | refused ("Hunk 1 FAILED") |

- git documents that `git apply` "expects … at least one line of context" and
  that `--unidiff-zero` lifts the checks. What the documentation does not say
  is that without the option an insertion in the middle of a file is not
  rejected but applied at its end. The eight other zero-context patches in the
  corpus are rejected. Anything that pipes `git diff -U0` into `git apply`
  needs the option.
- go-gitdiff: known, with a fix proposed in
  [#81](https://github.com/bluekeyes/go-gitdiff/pull/81) (open since July 2026).
- patch-ng: not found in the tracker.
- BusyBox patch also turns `@@ -1 +0,0 @@` on a ten-line file (delete the first
  line) into an empty file, with exit 0: it copies the rest of the file only
  when the hunk's new length is not zero. Its source says that it "does not
  use the location information", which is why the insertion lands at the end.

**`\ No newline at end of file`.** BusyBox patch (1.36.1 and 1.38.0) and
patch-ng read the marker and do nothing with it: a file that should end without
a newline ends with one (`git/newline/removed-at-end` and eleven more between
them). Both report success. patch-ng: not found in the tracker; its parser
ends a hunk when the counts of the header are reached, so a marker after the
last line never reaches the code that applies the hunk. For a file whose last
line is a version number, a hash or a key, that is a different file.

**Renames, copies and the tree as it was.** Every section of a patch describes
the tree as it was before the patch.

- GNU patch (2.7.6 and 2.8.1), given a patch that swaps two files with two
  crossing renames (`git/ops/swap-two-files-break-rewrites`), prints "patching
  file left.txt (already renamed from right.txt)" twice, changes nothing and
  exits with 0. A chain of three renames is left half-done with exit 1.
- libgit2 1.9.7, `git_apply` to the working directory: after a patch that
  copies a file which the patch does not otherwise change
  (`git/ops/copy-pure`), the copy exists and **the original is gone**. The call
  returns normally. The same happens with the files committed first, and with
  `GIT_APPLY_LOCATION_BOTH` the original leaves the index as well. Reproduced
  on `main` (42a89d7, October 2026) with tests: the source of a copy is put on
  the list of paths to check out, and since it is not part of the result, the
  checkout removes it. Not found in the tracker.
- libgit2 again: a patch for a file whose name contains a backslash
  (`git/paths/backslash`) is accepted, the call returns normally, and the file
  is unchanged. The cause is in checkout, not in apply: with
  `GIT_CHECKOUT_DISABLE_PATHSPEC_MATCH` the paths are literal, but the range
  for the iterators is still derived from them as from pathspecs, which removes
  the backslash. Any such checkout misses such a file; also on `main`. Not
  found in the tracker.
- patch-ng loses the source or the target of four renames and two copies, and
  writes a regular file where the patch creates a symbolic link.

**What a small `patch` does not read.** BusyBox patch takes the `---`/`+++`
lines and the hunks and ignores the rest of a git diff. Renames, copies, mode
changes, new empty files and `GIT binary patch` sections are skipped without a
word — the exit status is 0 and, for a binary patch, the file is simply still
the old one. A deleted file stays behind empty unless `-E` is given. Quoted
file names are not decoded, which makes it refuse those patches rather than
misapply them. 1.38.0, the current release, gives the same result as 1.36.1 on
every vector. GNU patch, for comparison, says "git binary diffs are not
supported" and exits with 1. I could not search the BusyBox tracker; this may
all be known and intended. It is here because it is the `patch` of Alpine
Linux and of many container images, where a build script that says `patch -p1`
gets it without asking.

**Line endings.** whatthepatch's `apply_diff` takes the old text apart with
`str.splitlines()` and returns a list of lines. A file with CRLF or CR line
endings comes back with LF (five vectors), and a file with a form feed, a
vertical tab or U+2028 in a line is refused, because the pieces no longer match
the patch.
patch-ng turns `git/bytes/lf-to-crlf` — a change of nothing but the line
endings — into no change.

**Names.** GNU patch cannot apply a change that only the `diff --git` line
names when the name contains a space (a pure rename, a mode change, a new
empty file: four refusals), nor one to a file whose name ends with a space.
And 2.8.1, which by design no longer creates files with a newline in the name,
ends on such a patch (`git/paths/newline`) in a segmentation fault after
printing the same error some eleven thousand times: its handler for fatal
errors tries to write the pending files once more, the same rename fails, and
the handler is entered again. 2.7.6 applies the patch. I could not search the
tracker of GNU patch either.

Two things held without exception: jsdiff's `applyPatch` applied all 184
patches it could be given and diffy's `apply_bytes` all 189, and
`git apply --unidiff-zero` applied all but the one that git 2.43 cannot read
(section 6).

## 14. Six more parsers: Rust and Java

Added after the sections above were written, and summarised here rather than
woven into them. The table at the top includes them. These were looked at
through their adapters only — each adapter is a direct call of the library, and
`node src/try.js <adapter> <vector-id> --raw` shows the answer as it came back.

- **diffy 0.5.2** (Rust) reads git's format through `PatchSet` with
  `ParseOptions::gitdiff()`: 217 of the 219 vectors in its scope agree, quoted
  names, binary patches, modes and mail signatures included, and as an applier
  it turns all 189 patches it can be given into the right file. The two
  differences: empty input is an error ("no valid patches found") rather than
  an empty list, and one mail fails — the signature of `git format-patch`
  directly after a hunk whose *deleted* last line carries `\ No newline at end
  of file` (`git-wrapped/format-patch-no-newline-then-signature`: "expected no
  more deleted lines"). Without the marker on the deleted line, or without the
  signature, the same text is read. Not found in the tracker. `gitdiff()` needs
  the `diff --git` line; GNU diffs are for `ParseOptions::unidiff()`, which
  reads all 17 of them.
- **patch 0.7.0 and gitpatch 0.7.1** (Rust, the second a fork of the first)
  decode the short escapes in a quoted name but not the octal ones, so every
  name outside ASCII stays escaped. A deleted line that reads `-- comment`
  ends in a panic, "bug: failed to parse entire input"
  (`git/content/deleted-double-dash-comment` and five more of the fourteen
  vectors of that kind), and a section without hunks — a mode change, a pure
  rename, a binary notice — makes the whole input a parse error. Known in
  part: patch [#23](https://github.com/uniphil/patch-rs/issues/23),
  [#24](https://github.com/uniphil/patch-rs/issues/24),
  [#25](https://github.com/uniphil/patch-rs/issues/25), all open since 2024.
- **unidiff 0.4.1** (Rust, a port of the Python library) keeps quoted names
  quoted, returns nothing for a section without `---`/`+++` lines, shares the
  `is_added_file` rule of section 4, and loses the no-newline marker when it
  follows the last line of a hunk — its source has a "FIXME: sync with
  upstream version" at that spot.
- **java-diff-utils 4.18** removes `a/` and `b/` itself, keeps quoted names
  quoted, cuts names at spaces when only the `diff --git` line carries them
  (`old name.txt` becomes `old`), and reads lines with `BufferedReader`, which
  ends a line at a lone carriage return too ("expected data line not found").
  As an applier it works on lists of lines, so a file with CRLF line endings
  comes back with LF (four vectors). Version 4.15 also put a zero-context
  insertion one line early, like go-gitdiff and patch-ng; that was fixed in
  [#236](https://github.com/java-diff-utils/java-diff-utils/pull/236), and
  4.18 applies those patches correctly.
- **diffparser 1.4** (Java, `io.reflectoring.diffparser`) does not count the
  lines of a hunk: the `diff --git` line of the next file becomes a context
  line of the hunk before it, and so does `\ No newline at end of file`. Many
  open issues describe the consequences
  ([#30](https://github.com/thombergs/diffparser/issues/30),
  [#35](https://github.com/thombergs/diffparser/issues/35)).

## 15. JGit and toybox patch

Added on 17 November 2026. Both were also run by hand: JGit with a program of
thirty lines that calls `Git.apply()` on the output of `git diff`, toybox on
the command line, with the released binary and with a build of its current
source.

**JGit 7.8.1** — `org.eclipse.jgit.patch.Patch`, the parser behind
`ApplyCommand` — reads 208 of the 224 vectors in its scope as git does: content that looks like a header, zero counts, binary patches, modes,
mails and merges are all right. The sixteen differences are about names: the
quoted name followed by a TAB (section 2), the name on the side where no file
exists (section 5), and a binary file in a `diff --cc` section, which gets no
name at all because only the `---`/`+++` lines are read for one there.

As an applier, `Git.apply()` gets 182 of 208 patches right, refuses 21 and
leaves one half-done. It applies four wrongly without an exception, in three
ways:

- **`@@ -1 +0,0 @@` empties the file.** That is what `git diff -U0` writes for
  "remove the first line". Applied to a file of ten lines, nine should remain;
  JGit leaves none (`git/ranges/u0-delete-first-line`). `PatchApplier` takes a
  hunk whose new range starts at 0 to be "the single hunk for clearing all
  content": it checks that the lines of the hunk are at the top of the file and
  then clears the file, however much comes after them.
- **A new file with a space and a non-ASCII letter in its name** is created
  under the name `\303\234bersicht 2024.txt"<TAB>` — backslashes, digits, a
  quote and a TAB — and success is reported
  (`git/paths/quoted-name-with-space-added`). A change to an existing file of
  that kind is refused, because no file of that name exists. With git's
  defaults this is every file called something like `Übersicht 2024.txt`.
  BusyBox patch and patch-ng create a misnamed file from the same patch
  (`\303\234bersicht 2024.txt"` and `234bersicht 2024.txt`); they do not
  unquote names at all.
- A symbolic link that a patch adds becomes a regular file containing the
  target (two vectors); patches that change or delete a link are refused.

Two more results say something about the method. A hunk without context that
deletes a single line (`@@ -8 +8,0 @@`) "cannot be applied": the position is
taken from the new range, which for a hunk without new lines names the line
before the change (`gnu/u0`). And when one file of a patch fails, the others
have already been written (`gnu/new-and-deleted-files`); `git apply` changes
nothing in that case. Seven more refusals are the adapter's: `ApplyCommand` has
no equivalent of `-p0` or `-p2`.

Upstream: nothing found in the issues of eclipse-jgit/jgit. The older Eclipse
Bugzilla showed a "temporary shutdown" page when I looked.

**toybox patch 0.8.15** is the `patch` of Android, and the ancestor of the
BusyBox applet ("Adapted from toybox's patch implementation"). 136 of 208
patches are right, 27 are refused, 38 are wrong with exit status 0.

- **`@@ -1 +0,0 @@` deletes the file** ("removing f.txt"). A first hunk whose
  new range is `+0,0` is taken to mean that the file is deleted — which is true
  when the hunk has context, and not when it was made with `-U0`. BusyBox
  leaves the file empty in the same case, JGit too (above); GNU patch and
  `git apply --unidiff-zero` remove one line.
- **`\ No newline at end of file`** after the last line of a hunk is dropped,
  and every line of a hunk is written with a newline: a file that should end
  without one ends with one, also when its last line is only context of the
  hunk. A marker in the middle of a hunk (the old side lacks the newline) makes
  the hunk fail.
- **A NUL byte ends the line.** `key\0VALUE` in a hunk written by
  `git diff --text` comes out as `key`, with exit status 0
  (`git/bytes/nul-with-text-option`). BusyBox refuses that patch.
- Hunks without context are refused unless they cover the whole file, because
  hunks are located by their content, not by their line numbers.
- Renames, copies, mode changes, new empty files, symbolic links and
  `GIT binary patch` sections are skipped with status 0, as in BusyBox. The
  source lists "git syntax (rename, etc)" as to do.

Unlike BusyBox, toybox unquotes file names, so the patches for files with
names outside ASCII apply. Upstream: nothing found in the GitHub issues of
landley/toybox; I did not search the mailing list.

## Smaller observations

- jsdiff returns one empty entry for empty input (`parsePatch('')` is
  `[{hunks: []}]`).
- unidiff reports a copy (`copy from`/`copy to`) as a rename.
- gitdiff-parser reports a rename that also changes content as `modify`, and
  does not read `old mode`/`new mode`.
- parse-diff cuts a file name at anything that looks like a timestamp
  (`report 2024-01-01 10:00:00 +0100.txt` becomes `report`).
- libgit2 rejects NUL bytes in content shown with `--text`.
- what-the-diff throws on the `dissimilarity index` line of `git diff -B`.
- whatthepatch leaves the `a/` on names it takes from the header of a rename
  that has no hunks.

## What held up

- Eighteen of the twenty-five libraries get every "content that looks like a
  header" vector right; counting the lines of a hunk has become the norm.
- diffy 0.5.2 differs from git on two of 219 vectors as a parser and on none
  of 189 as an applier.
- GitPython, which only reads file headers and always asks git for one fixed
  format, agreed on all 181 vectors of the `git` tier.
- go-gitdiff 0.9.0, and the fork of it inside gitleaks, agreed on all 198
  vectors in their scope (`git` and `git-wrapped`) and on 23,182 random
  scenarios each — the only parsers without a single difference there.
- trufflehog is unaffected by the git configuration of whoever runs it.
- jsdiff 9, whose git support is recent, is the only JavaScript parser that
  decodes quoted names, and documents its limits in its source.
- libgit2 decodes quoted names and handles line endings, form feeds, Unicode
  line separators and no-newline markers without a single difference; its
  problems are in headers — sections without hunks, and names with spaces.

## How much to trust this

The expectations are not my reading of the format. Each one was established by
applying the parsed hunks to the old file contents and comparing the result,
byte for byte, with the new contents; by comparing files, modes and counts with
`git diff --raw` and `--numstat`; and by asking `git apply --numstat` to read
the same text. Two independent implementations of the reference parser, in
JavaScript and Python, agree on all vectors and on 32,729 further random
scenarios (47,215 scenarios were verified against ground truth in total).
[`README.md`](README.md#why-trust-the-expectations) has the details.

For applying, the expectation is not computed at all: it is the tree the diff
was made to. The reference applier reaches it for all 208 patches, and
`test/apply.test.js` damages trees in sixteen ways and requires each to be
noticed.

What is not verified by a machine is the fairness of each adapter. That is
where a second pair of eyes is most useful.
